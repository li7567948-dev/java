# Лабораторная работа № 3 — исключения и коллекции (Java)

**Тема:** пункт пропуска автомобилей. Развитие лабораторной работы № 2 без замены предметной области.

**База проекта:** исходные `lab2/src` из репозитория `li7567948-dev/java` (ветка `main`, октябрь 2026).

## Архитектура и наследование от ЛР2

- `model/Vehicle.java` + `CargoCheck`: те же габариты, груз, скорость, время проверки и правила пропуска.
- Подклассы `Car`, `Truck`, `Bus`, `Trailer`, `CarWithTrailer`: **все пять** сохранены. Ограничения автобуса, трейлера и автомобиля с прицепом не заменены упрощённой моделью.
- `CheckPoint`: один физический пункт проверки; `Simulation`: набор пунктов, очередь транспорта, события и статистика. Поэтому **главный класс для коллекций — `Simulation`**, содержащий иерархию объектов.
- `VehicleFactory`, `Generator`, `CheckResult`, `Event`: принципы ЛР2 сохранены.
- `view/ConsoleView`: только отображение/ввод; `controller/Controller`: действия меню, разбор данных, вызов служб; `controller/ErrMsgLog`: единая обработка ошибок и запись журналов.

Сохранены пункты меню ЛР2: 1 — готовые автомобили, 2 — собственный автомобиль, 3 — моделирование очереди.

## Запуск в Eclipse

1. `File > Import > General > Existing Projects into Workspace`.
2. Выбрать папку `lab3` (в ней находятся `.project` и `.classpath`).
3. `Project > Clean` и убедиться, что IDE использует JDK 8 или более новый.
4. Запустить `src/controller/Main.java` → **Run As > Java Application**.
5. По умолчанию откроется исходное меню ЛР2 с новыми пунктами 4–6. Для отдельного режима можно задать аргумент в `Run Configurations > Arguments`.

Если в Workspace уже есть старый проект `lab3`, сначала убрать старый проект из Workspace и импортировать этот, **не смешивая** файлы двух версий.

## Командная строка

В корне проекта:

```sh
javac -encoding UTF-8 -d bin src/model/*.java src/controller/*.java src/view/*.java src/tests/*.java
java -cp bin controller.Main                  # меню
java -cp bin controller.Main --benchmark      # 10 полных логов
java -cp bin controller.Main --solvability    # отдельный режим разрешимости
```

**Java 8+; сторонние библиотеки не используются.** Для Windows предусмотрены `run_tests_windows.bat` и `run_benchmark_windows.bat` (требуется установленный JDK и `javac` в PATH).

## Методика измерений

`System.nanoTime()` измеряет только вызовы `ArrayList.add`, `ArrayList.set`, `HashMap.put`, `HashMap.replace`. Генерация объектов, запись в файл, выбор случайных индексов и вычисление статистики выполняются **вне** этого интервала. Время **в наносекундах**; каждый элемент и операция записываются отдельной строкой.

Индексы изменения выбираются частичной тасовкой Фишера–Йетса, поэтому ровно 10% индексов различны. `addTotalTime` — сумма измерений; `addAverageTime` — среднее арифметическое, `addMedianTime` — медиана. Аналогично `set/put/replace`; `allOperationsTotalTime` — сумма операций двух типов. Имена `Median` и `Average` не смешиваются.

Полные 10 логов генерируются программой, а также приложены в ZIP-версии проекта. Большие автоматически генерируемые файлы `*.log` исключены из Git посредством `.gitignore`.

## Ограничения и честная интерпретация результатов

- Время коротких операций чувствительно к JIT, сборке мусора, состоянию процессора и разрешению таймера. Одна серия — демонстрационный эксперимент, не строгий статистический тест производительности.
- Приведённая в пособии формула изменения `ArrayList` относится к старым реализациям и не гарантируется Java API. Внутреннее поле `capacity` не читается через reflection: график замеров не доказывает фактический размер массива.
- `--solvability` проверяет окончание проверок к сроку; запреты на въезд остаются самостоятельной проверкой `Vehicle.pass()`.
- Не изменяются физические ограничения машин, количество установленных пунктов и продолжительность проверки.
- Требование 7.3 не выполнено до тех пор, пока студент не приложит свою подлинную историю запросов и публично доступную ссылку.
